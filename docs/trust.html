Trust & Data Handling

How ActionBoundary handles redacted traces.

The review is designed so a buyer can ask hard security questions without requiring production access, real customer data, shared credentials, or third-party model processing by default.

Staging or sandbox only No production credentials No third-party LLMs by default 30-day deletion default

STORAGE Encrypted, access-controlled storage with access limited to the named reviewer unless otherwise agreed.

Short version for security review.

The engagement is intentionally narrow: one staging workflow, trace-backed authorization evidence, and a report that separates public model-behavior research from customer-specific runtime evidence.

No production access

Reviews use staging, sandbox, exported logs, or redacted traces. Production systems are out of scope by default.

No shared credentials

Do not send passwords, API keys, session tokens, private keys, or unrestricted admin accounts.

No customer data by default

Use synthetic, de-identified, or redacted data. Harmless canaries replace real secrets.

30-day deletion default

Client traces are deleted within 30 days after final report delivery, or sooner on written request.

No third-party LLMs by default

Client traces are not sent to model providers or shared analysis tools unless approved in writing.

Default subprocessors: none

Trace analysis is local by default. Any third-party processing path requires written approval first.

Data handling ledger.

These are the default controls. Contract terms can replace or tighten them for a specific engagement.

Data requested

One redacted trace or exported log for the first scoreability diagnostic; later, staging traces for selected scenarios if the workflow is ready.

Transfer

Use a customer-approved secure channel, such as a client portal, encrypted file share, private repository, or agreed secure link.

Storage

Traces are kept on encrypted, access-controlled local storage after receipt. Access is limited to the named reviewer unless otherwise agreed in writing.

Use limits

Client traces are not used for model training, public examples, benchmark data, marketing claims, or third-party disclosure without explicit written permission.

Retention

Default retention is deletion within 30 days after final report delivery, or sooner on written request. Deletion confirmation is available on request.

Third-party LLMs

Client traces are not sent to third-party LLMs or model providers by default. If your team requests or approves LLM-assisted analysis or another third-party processing path, it requires written approval and minimized, redacted inputs.

Contracts

Reasonable NDA, MSA, DPA, or BAA terms can be reviewed when the engagement requires them.

What not to send.

Private trace review works best when sensitive data never enters the package in the first place.

  • Production credentials, API keys, tokens, private keys, or session cookies.
  • Real customer data, PHI, PII, payment card data, or regulated financial account data.
  • Raw database dumps, production ledger IDs, production bank details, or unrestricted admin accounts.
  • Private traces through public GitHub issues, public pull requests, or public discussions.

Clear scope, clear limits.

This is a focused authorization-boundary review, not a broad certification claim.

What the review covers

Whether a tool-using agent can take a high-impact action without trusted, current, scope-matching authorization evidence.

What the review does not claim

It is not a SOC 2 audit, HIPAA assessment, PCI assessment, full penetration test, SAST, secret scan, or full IAM/MCP configuration audit.

When sensitive traces may be possible

If sensitive data could appear, we pause first and handle redaction, de-identification, NDA, DPA, or BAA requirements before transfer.

Questions before sharing a trace?

Send the data-handling question first. The safest pilot is the one where the transfer path, redaction boundary, and retention rule are clear before the first file moves.
